# 01. Архітектура, Виконавчий Код Конструкторів та Фізична Розмітка Пам'яті

## 1. Фізична Розмітка Пам'яті (Memory Layout & Alignment)

Для запобігання міжядерному ефекту **False Sharing (Cache Line Bouncing)** під час паралельного виконання атомарних операцій, структурні елементи буфера вирівнюються за допомогою адаптивного педдінгу `cpu.CacheLinePad` (пакет `golang.org/x/sys/cpu`). Це забезпечує сумісність як з архітектурою **x86-64** (розмір кеш-лінії 64B), так і з **ARM64** (розмір кеш-лінії 128B, наприклад Apple Silicon M1-M4, AWS Graviton).

---

### 1.1 Фізична розмітка `SPSCRingBuffer[T]` (Single-Producer Single-Consumer)

В SPSC-патерні масив даних є максимально щільним (*Compact Dense Array*) для максимізації просторової локальності (*Spatial Locality*) та використання апаратного префетчера (*Hardware Prefetcher*). Атомарні змінні продюсера та споживача винесені на окремі кеш-лінії разом із локальними тіньовими лічильниками (*Shadow Counters*).

| Зсув (ARM64 / 128B) | Зсув (x86-64 / 64B) | Поле структури | Розмір | Призначення та Cache Line Isolation |
| :--- | :--- | :--- | :--- | :--- |
| `0x000 .. 0x007` | `0x00 .. 0x07` | `tail atomic.Uint64` | 8 B | **Producer Hot Path:** Позиція запису |
| `0x008 .. 0x00F` | `0x08 .. 0x0F` | `headCache uint64` | 8 B | Тіньова локальна копія `head` (без Atomics) |
| `0x010 .. 0x08F` | `0x10 .. 0x4F` | `_ cpu.CacheLinePad` | 128B / 64B | **Cache Line 1:** Ізоляція гарячого шляху Producer |
| `0x090 .. 0x097` | `0x50 .. 0x57` | `head atomic.Uint64` | 8 B | **Consumer Hot Path:** Позиція читання |
| `0x098 .. 0x09F` | `0x58 .. 0x5F` | `tailCache uint64` | 8 B | Тіньова локальна копія `tail` (без Atomics) |
| `0x0A0 .. 0x11F` | `0x60 .. 0x9F` | `_ cpu.CacheLinePad` | 128B / 64B | **Cache Line 2:** Ізоляція гарячого шляху Consumer |
| `0x120 .. 0x127` | `0xA0 .. 0xA7` | `mask uint64` | 8 B | Read-Only конфігурація ємності (`capacity - 1`) |
| `0x128 .. 0x12B` | `0xA8 .. 0xAB` | `state atomic.Uint32` | 4 B | Атомарний прапорець стану буфера |
| `0x12C .. 0x1AB` | `0xAC .. 0xEB` | `_ cpu.CacheLinePad` | 128B / 64B | **Cache Line 3:** Ізоляція конфігурації |
| `0x1AC .. 0x1C3` | `0xEC .. 0x103` | `ring []T` | 24 B | Дескриптор слайсу вказівників (Pointer, Len, Cap) |

### 1.2 Фізична розмітка `MPMCRingBuffer[T]` та `SlotPadded[T]` (Multi-Producer Multi-Consumer)

В MPMC-патерні за алгоритмом Дмитра В'юкова конкурентні продюсери та споживачі паралельно оновлюють атомарні послідовності `sequence` у сусідніх комірках. Щоб запобігти каскадним RFO-штормам (*Request For Ownership*) між ядрами CPU, кожен слот масиву гарантовано відокремлений педдінгом.

#### Розкладка структури слота (`SlotPadded[T]`):

```go
type SlotPadded[T any] struct {
	sequence atomic.Uint64 // 8 Bytes (Атомарний стан бар'єра)
	val      T             // N Bytes (Дані типу T)
	_        cpu.CacheLinePad // 128B (ARM64) / 64B (x86-64)
}
```

#### Розкладка головного буфера (`MPMCRingBuffer[T]`):

| Зсув (ARM64 / 128B) | Зсув (x86-64 / 64B) | Поле структури | Розмір | Призначення та Cache Line Isolation |
| :--- | :--- | :--- | :--- | :--- |
| `0x000 .. 0x007` | `0x00 .. 0x07` | `head atomic.Uint64` | 8 B | **Cache Line 1:** Атомарний голова споживачів |
| `0x008 .. 0x087` | `0x08 .. 0x47` | `_ cpu.CacheLinePad` | 128B / 64B | Ізоляція `head` від інших полів |
| `0x088 .. 0x08F` | `0x48 .. 0x4F` | `tail atomic.Uint64` | 8 B | **Cache Line 2:** Атомарний хвіст продюсерів |
| `0x090 .. 0x10F` | `0x50 .. 0x8F` | `_ cpu.CacheLinePad` | 128B / 64B | Ізоляція `tail` від інших полів |
| `0x110 .. 0x117` | `0x90 .. 0x97` | `mask uint64` | 8 B | Read-Only конфігурація ємності (`capacity - 1`) |
| `0x118 .. 0x11B` | `0x98 .. 0x9B` | `state atomic.Uint32` | 4 B | Атомарний прапорець стану буфера |
| `0x11C .. 0x19B` | `0x9C .. 0xDB` | `_ cpu.CacheLinePad` | 128B / 64B | **Cache Line 3:** Ізоляція конфігурації |
| `0x19C .. 0x1B3` | `0xDC .. 0xF3` | `slots []SlotPadded[T]` | 24 B | Дескриптор масиву ізольованих слотів |

## 2. Покроковий Виконавчий Код Конструкторів

Нижче наведено виконання конструкторів при запиті ємності $N = 5$ для типу $T = \text{int}$ (`NewSPSCRingBuffer[int](5)` та `NewMPMCRingBuffer[int](5)`).

### 2.1 Конструктор `NewSPSCRingBuffer[T]`

```go
func NewSPSCRingBuffer[T any](capacity uint64) (*SPSCRingBuffer[T], error) {
	// Вхідні дані: capacity = 5

	// Крок 1: Валідація граничних умов
	if 5 == 0 { return nil, ErrInvalidCapacity } // false
	if 5 > maxCapacity { return nil, ErrCapacityTooLarge } // false (5 <= 2^62)

	// Крок 2: Округлення до степеня двійки (Power-of-Two Alignment)
	// (5 & (5 - 1)) => (5 & 4) = 4 != 0 (значення не є степенем двійки)
	if (5 & (5 - 1)) != 0 {
		// bits.Len64(5 - 1) = bits.Len64(4) = 3 (двійкове "100" має довжину 3 біти)
		// 1 << 3 = 8 (00001000_2)
		capacity = 1 << uint64(bits.Len64(5-1)) // capacity = 8
	}

	// Крок 3: Обчислення побітової маски
	// mask = 8 - 1 = 7 (00000111_2)
	mask := capacity - 1

	// Крок 4: Аллокація щільного масиву в купі (Heap Allocation)
	// 8 елементів * 8 байтів/int = 64 байти чистої пам'яті під дані
	ring := make([]int, 8)

	// Крок 5: Повернення вказівника (Escapes to Heap)
	return &SPSCRingBuffer[int]{
		mask: mask,
		ring: ring,
	}, nil
}
```

### 2.2 Конструктор `NewMPMCRingBuffer[T]`

```go
func NewMPMCRingBuffer[T any](capacity uint64) (*MPMCRingBuffer[T], error) {
	// Вхідні дані: capacity = 5

	if 5 == 0 { return nil, ErrInvalidCapacity }
	if 5 > maxCapacity { return nil, ErrCapacityTooLarge }

	// Округлення: 5 -> 8 (2^3)
	if (5 & (5 - 1)) != 0 {
		capacity = 1 << uint64(bits.Len64(5-1)) // capacity = 8
	}

	mask := capacity - 1

	// Крок 1: Аллокація масиву вирівняних слотів SlotPadded у купі
	// 8 слотів * 144B/слот (на ARM64) = 1152 байти в Heap
	slots := make([]SlotPadded[int], 8)

	// Крок 2: Ініціалізація інваріанта послідовностей (Vyukov Sequence State)
	// BCE Hint: Створення локального зрізу для усунення перевірок меж (Bounds Check Elimination)
	subSlots := slots[:capacity]
	for i := uint64(0); i < capacity; i++ {
		// Установка початкового бар'єра: slots[i].sequence = i
		// slots[0].sequence = 0, slots[1].sequence = 1, ..., slots[7].sequence = 7
		subSlots[i].sequence.Store(i)
	}

	return &MPMCRingBuffer[int]{
		mask:  mask,
		slots: slots,
	}, nil
}
```

## 3. Розширений Q&A: Системний & Мікроархітектурний Аналіз

### Q1: Чому побітова операція `index & mask` працює ідентично `index % capacity` і чому вона швидша?

**Відповідь:**

Коли ємність буфера $N$ є степенем двійки ($N = 2^k$), її двійкове представлення має вигляд $100\dots0_2$ з $k$ нулями. Маска $M = N - 1$ складається строго з $k$ молодших одиничних бітів ($011\dots1_2$).

Застосування інструкції `AND` з маскою обнуляє всі старші біти числа ($\ge 2^k$), залишаючи лише молодші $k$ бітів, що математично еквівалентно остачі від ділення $X \pmod{2^k}$.

**Порівняння на рівні інструкцій CPU:**
- **Цілочисельне ділення (`%`):** Транслюється в інструкцію `DIV` / `IDIV` (x86-64) або `SDIV` (ARM64). Ця інструкція є неконвеєризованою (*Unpipelined Execution*) і виконується за 20–40 тактів CPU.
- **Побітове `AND` (`&`):** Транслюється в інструкцію `AND`. Вона виконується за 1 такт CPU у будь-якому АЛУ (*Arithmetic Logic Unit*) із пропускною здатністю до 4 інструкцій за такт.

```text
Приклад для tail = 13, capacity = 8 (mask = 7):

  13 : 0000 1101_2
&  7 : 0000 0111_2  (mask = 8 - 1)
----------------
   5 : 0000 0101_2  (результат: індекс 5)
```

Округлення ємності виконується через `bits.Len64(capacity - 1)`, що компілюється в апаратні інструкції пошуку провідних нулів: `LZCNT`/`BSR` (x86-64) або `CLZ` (ARM64), які виконуються за 1 такт.

### Q2: Чому ми відмовилися від фіксованого педдінгу `_ [56]byte` на користь `cpu.CacheLinePad`?

**Відповідь:**

Використання фіксованих масивів `_ [56]byte` спирається на застаріле припущення, що кеш-лінія $L1D$ на всіх CPU дорівнює 64 байтам. Це створює дві критичні проблеми:

1. **Мікроархітектурна несумісність (ARM64 / Apple Silicon / IBM POWER):**
   На сучасних процесорах ARM64 (Apple M1/M2/M3/M4, Fujitsu A64FX) розмір кеш-лінії $L1D$ або блоку вибірки $L2$ становить 128 байт. При використанні `_ [56]byte` зміщення `head` та `tail` потрапляють усередину однієї 128-байтної кеш-лінії. Це призводить до прихованого False Sharing та деградації продуктивності під навантаженням.

2. **Помилки вирівнювання (Alignment Drift):**
   Сума розмірів полів при ручному розрахунку часто викликає переповнення. Наприклад, `mask uint64` (8B) + `state atomic.Uint32` (4B) + `_ [56]byte` = 68 байт. Це переповнює 64B кеш-лінію і зміщує всі наступні поля.

`cpu.CacheLinePad` під час компіляції підставляє масив `_ [64]byte` для `GOARCH=amd64` або `_ [128]byte` для `GOARCH=arm64`, стверджуючи точний кросплатформений ізоляційний бар'єр.

### Q3: Чому SPSC та MPMC вимагають кардинально різних розкладок пам'яті (Spatial Locality vs False Sharing)?

**Відповідь:**

В основі дизайну лежить фундаментальний інженерний компроміс між щільністю даних у L1-кеші та міжядерним контеншеном (*Contention*):

- **SPSC (Однопотоковий запис та читання):**
  Конкуренція за слоти між різними ядрами відсутня за визначенням. Використання педдінгу всередині масиву шкідливе: воно роздуває розмір буфера і викликає каскадні витіснення даних з L1D кешу (*L1 Cache Evictions*). Щільний масив `[]T` дозволяє вмістити до 8-16 елементів в одну кеш-лінію, максимізуючи ефективність апаратного префетчера (*Hardware Stream Prefetcher*).

- **MPMC (Багатопотоковий запис та читання):**
  Декілька ядер одночасно виконують CAS та Atomic Store над сусідніми елементами масиву. Якщо слоти лежать в одній кеш-лінії, ядро-переможець надсилає в шину Interconnect сигнал RFO (*Request For Ownership*), що інвалідує цю лінію у L1D-кешах усіх інших ядер (*Cache Line Bouncing*). Для MPMC ми свідомо жертвуємо щільністю RAM ($87.5\%$ обсягу структури йде на педдінг `SlotPadded`), щоб ізолювати атомарний стан слотів і повністю ліквідувати RFO-шторм.

### Q4: Чому аналізатор Go (`-m -m`) показує, що буфер та його слайси витікають у купу (Escape Analysis), і чи є це проблемою?

**Відповідь:**

Аналіз витоків компілятора `gc` демонструє:

```text
./buffer/ring_buffer.go:80:9: &buffer.SPSCRingBuffer[...]{...} escapes to heap
./buffer/ring_buffer.go:82:13: make([]int, capacity) escapes to heap
```

**Причина витоку:** Конструктори повертають вказівник на структуру (`*SPSCRingBuffer`). Оскільки час життя створеного об'єкта перевищує тривалість стекового фрейму конструктора (*Stack Frame Scope*), компілятор змушений виділити пам'ять у Heap. Слайс `make()` записується всередину цієї структури і транзитивно витікає разом із нею.

**Оцінка впливу:** Це бажана та оптимальна поведінка. Кільцеві буфери є фундаментальними довгоживучими об'єктами системи (*Long-Lived Infrastructure Entities*). Вони ініціалізуються один раз при старті додатка (*Warmup Phase*). Оскільки під час виконання `Push`/`Pop` нові аллокації не створюються (*Zero-Allocation Runtime Contract*), разовий витік при конструкції має нульовий вплив на GC Pauses та затримки гарячого шляху (*Hot Path Latency*).

### Q5: Чому для MPMC необхідний цикл ініціалізації `sequence`, а для SPSC — ні?

**Відповідь:**

- **В SPSC:** Масив даних не містить внутрішніх атомарних лічильників. Синхронізація здійснюється виключно через зовнішні покажчики `head` та `tail`. Автоматичного обнулення пам'яті Go Runtime (`make([]T)`) достатньо.

- **В MPMC (Алгоритм В'юкова):** Кожен слот керується власним бар'єром послідовності `sequence atomic.Uint64`. Алгоритм вимагає суворого початкового інваріанта:
  $$\text{slot}[i].\text{sequence} = i \quad \forall i \in [0, N-1]$$
  Якщо не виконати цикл `sequence.Store(i)`, усі слоти будуть містити 0. При спробі виклику `Push` для індексу $tail = 1$ перевірка стану слота $diff = \text{seq} - tail = 0 - 1 = -1$ дасть результат $diff < 0$. Буфер сприйме порожні слоти як "повні" і перейде у стан вічного блокування (*Deadlock / False Full Condition*).
